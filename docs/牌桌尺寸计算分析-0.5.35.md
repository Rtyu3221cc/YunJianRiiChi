# 牌桌尺寸计算分析（第10项，只分析）

你的理解基本正确：桌面牌应共享一套模型与尺寸基准，靠相机透视、位置和朝向产生视觉差异。当前项目除了这些差异，还用了不同的宽度常量，以及自家副露的屏幕投影拟合，所以确实存在额外的不统一。本项没有修改全局尺寸规则；本次只按第8项修正流局自家摊牌。

## 现在怎样计算

`OriginalTiles` 从APK的 `mjp_new` 网格加载顶点，并把原模型宽度归一化到1。原始包围盒约为宽0.029479、长0.039133、厚0.019136（模型单位）；归一化后，长／宽约1.3275，厚／宽约0.6492。`CreateTable` 再把整个模型乘以调用方传入的宽度 `w`，因此实际长厚跟随原模型比例。`TableRenderer.Tile` 的旧参数 `h` 没有用于改变网格高度，调整这个参数不会改变牌的比例。

|显示对象|当前尺寸来源|额外处理|
|---|---|---|
|牌河|普通牌宽0.33|横放立直牌用0.44作为排布占位；模型横转90度|
|其他玩家站立手牌|宽0.29，中心间距0.31|原模型转为站立；位于不同桌边|
|一般副露|宽0.35|横放牌改变占位；加杠叠牌提高位置|
|自家副露|先宽0.35|再拟合真实模型／描边的屏幕宽度，目标是自家二维手牌宽度的0.98倍；这是额外缩放，不能只比较0.35和0.33|
|和牌摊牌|自家0.35、其他玩家0.29|自家间距0.37、其他0.31，按玩家方向旋转|
|流局摊牌|此前自家也用0.29；本次按第8项改为0.35|与自家和牌摊牌相同宽度／间距；听牌摊开和未听牌扣下采用不同桌边位置|
|拔北牌|先宽0.35|根据玩家副露的投影面积缩放，倍率限制0.6～1；本次仅把摆放间距改为缩放后的实际宽度|
|自家前景手牌|独立二维四边形，高2.54、宽2.54×0.62|使用另一台正交相机，orthographicSize=9；它不属于桌面三维模型的0.29／0.33／0.35尺寸体系|

自家前景手牌在完整安全区、倍率为1时，单牌像素高度约为 `Screen.height × 2.54 / 18`，像素宽度约为 `Screen.height × 1.5748 / 18`。屏幕过窄时还会按安全宽度限制缩放。

桌面三维牌使用透视相机。未旋转的横向长度，像素尺寸近似为 `世界长度 × Screen.height / (2 × tan(FOV/2) × 相机深度)`；牌面有倾角／旋转时还要投影顶点。距离相机更远的牌看起来更小，同一张牌立起来和推倒也会有不同的屏幕长宽。这部分变化是正常透视，不等同于模型尺寸发生改变。

## 从雀魂APK能确认什么

已提取并核对原始网格、材质、手牌纹理、相机参数和场景锚点。桌面牌共用 `mjp_new` 模型；前景手牌采用单独的正交展示与不同手牌纹理；拔北原始锚点间隔为0.0355模型单位。它们说明雀魂也把三维桌面牌和二维前景手牌分开处理，并通过场景坐标与相机统一展示。

APK中的相关Lua是加密字节数据，不能把已有的移植适配代码说成已完整恢复的雀魂源码。当前可核验的是上述网格、场景／UI参数及导出的曲线；还不能证明原游戏每个牌组在运行时都采用相同的局部缩放值。

本项目的额外不统一主要在：0.29／0.33／0.35三个宽度入口，自家副露为了贴近前景手牌而做的额外投影缩放，以及拔北独立的缩放上限。以后若要统一，应先建立“原模型尺寸＋每种摆放姿态＋相机”的统一基准，再独立保留二维前景手牌；不能把所有画面中的牌强行设成同一像素大小。这一轮没有实施该全局调整。
