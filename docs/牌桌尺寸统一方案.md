# 牌桌尺寸统一方案：保留现有布局锚点

核对基线：0.5.36，提交 `fe4f470cee984ae0f851e61cb81e1fe3ae2684b9`。本文件是本次代码、APK资源和参考视频的分析结果，尚未实施尺寸重构。

## 自摸牌为什么看起来偏小

当前 `TableRenderer` 已经使用雀魂APK的牌模型和桌面透视相机。需要整理的是叠加在它们之上的尺寸控制。

|比较对象|当前代码|含义|
|---|---|---|
|对手自摸牌与牌河|自摸0.29，牌河0.33|模型宽度本身相差约12.1%，投影还会叠加距离和朝向的影响|
|自家自摸牌与摊开的自家手牌|均为0.35|落地后处于相同桌边深度和相同朝向；代码没有为这一张自摸牌额外缩小|
|对手自摸牌与该对手摊开的手牌|均为0.29|侧边玩家的排布沿相机深度延伸，靠远端的自摸牌可以自然略小|
|自家摊牌与自家副露|基础宽度均为0.35|副露还通过父节点缩放拟合前景手牌的屏幕宽度，最终实际尺寸不一定相同|
|三维摊牌与自家操作手牌|前者使用桌面透视，后者使用独立正交相机|不能直接用像素宽高判断模型是否同尺寸|

自摸动作中的临时牌先按0.33生成，再按落地目标的碰撞盒宽度调整。当前目标节点没有额外父级缩放，所以这条路径目前能匹配目标；一旦改为组级缩放，只取碰撞盒的局部宽度就可能再次失配。这是统一尺寸时应一起消除的隐患，不能只改落地那张牌的常量。

用现有APK牌面顶点和现有相机参数作数值投影，在1688×780、13张摊牌的示例中：自家末张手牌与自摸牌的投影高度相同；四人桌右侧自摸牌比相邻末张手牌的投影高度约小4.0%。后者的模型宽度相同，差异来自自摸牌处于更远的一端。数值投影不是新生成的Unity运行截图，也不能替代对用户所指具体画面的定位。计算结果保存在 `build/tile-size-analysis/projection.json`。

## 雀魂资源能支持的结论

APK导出的 `mjp_new` 网格原始尺寸约为宽0.029479、长0.039133、厚0.019136。当前项目沿用了它的几何比例、桌面相机位置和旋转；另有独立的前景手牌场景、正交相机及手牌纹理。

原始牌预制体和导出场景中的该牌节点局部缩放为1。已核对 `自己自摸.mp4` 和 `其他玩家自摸.mp4` 的摊牌阶段。相关Lua仍是加密字节，现有证据不能证明雀魂运行时所有牌组都没有缩放，也不能将我们自己的适配公式称为雀魂原始源码。

## 推荐改动边界

1. 保留牌河、手牌区、副露区和拔北区当前布局锚点，以及用户已认可的自家副露位置。尺寸变化后的组内间距从模型宽度、横放占位和描边计算，避免牌互相穿插。
2. 建立一个桌面牌几何基准：宽、长、厚从同一个原模型取得，统一单位换算。用参考画面校准这个基准，把已放大的自家副露作为验收约束。
3. 每张牌的位置／朝向与尺寸分离。布局父节点保持单位缩放，尺寸应用于模型；碰撞盒、阴影、描边、横放占位和叠杠高度均从同一尺寸结果生成。这样调整尺寸不会连带缩放整组坐标。
4. 自摸、出牌、拔北、吃碰杠动画读取对应落地牌的实际几何尺寸。临时牌不再另用0.33等默认值，动画结束时也不重新计算另一套大小。
5. 让近大远小由现有透视相机产生，移除重复的按像素拟合／缩小补丁。独立的二维操作手牌保留自己的展示规则。
6. 先迁移自摸牌和和牌／流局摊牌，再迁移副露、牌河、拔北和动画。每步对比三人／四人、四个方向、站立／摊开／扣牌，以及动画携带／落地两个阶段，确认布局锚点和已认可的副露观感。
